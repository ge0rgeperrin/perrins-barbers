A

The idea in one paragraph

Perrin's already runs its diary, staff, prices and availability inside Schedulista. Rebuilding any of that would be expensive, fragile, and would leave the shop with two sets of prices to keep in step. So we don't. We build a presentation layer that reads the public Schedulista page three times a day, turns it into a clean JSON file, and renders it as a proper barbershop price list. Every "Book" button hands the customer straight back to Schedulista — deep-linked to the exact barber and service they tapped, so they land on the time picker, not the front page.

The consequence that matters to the owners: when David changes a price in Schedulista, the website and both apps change too, on their own, with nobody touching code.

Why one codebase, not two

Expo with Expo Router compiles the same React components to a native iOS app, a native Android app, and a statically pre-rendered website. For a site this size — five screens of mostly fixed content — a separate web codebase would double every future edit for no gain. One repo, one design system, one git push.

Escape hatch: if the web build ever needs heavier SEO or CMS-driven landing pages, the same components lift into Next.js without a rewrite. Don't do it pre-emptively.

B

What we deliberately do not build

Naming this up front stops it creeping back in halfway through.

Not buildingWhy
A booking engineAvailability, double-booking, staff rotas, cancellations and reminders stay in Schedulista. We build the interface to them (section C2) and drive their flow from our server — we never keep a second diary.
Payments or depositsCard handling drags in PCI scope and Apple's in-app purchase rules. If deposits are ever wanted, turn them on inside Schedulista.
Customer accounts or loginsSchedulista already holds the customer record. A second account system is a support burden with no payoff.
A live availability calendar on our sideIt would be stale the moment a walk-in books. Availability is only ever shown by Schedulista itself.
A backend serverThere is no server. A scheduled job writes a JSON file; static hosting serves it. Nothing to patch, nothing to pay for, nothing to go down at 2am.

C2 · The DOM shape we parse

The services block is a flat sequence of h3 provider headings, each followed by a dl of that provider's services. Verified structure:

perrins1.schedulista.com — actual markup, abridged
<div class='services-list'>
  <h3>Senior Barber - David</h3>
  <dl>
    <dt>
      <a class="widget-nav"
         href="https://www.schedulista.com/schedule/perrins1/choose_time?provider_id=1074010081&amp;service_id=1074625165">
        Under 14’s Haircut - £23.50 (Skin Fade +£5)
      </a>
    </dt>
    <dd class='service-description'></dd>
    ...
  </dl>
  <h3>Barber - Ben</h3>
  <dl> ... </dl>
</div>

Three things to note, because each one is a bug if missed:

  • Apostrophes are typographic (U+2019), not ASCII. Normalise them, or Under 14’s will never match Under 14's in an overrides file.
  • The name, the price and the surcharge note all live in one link label — Men's Haircut - £24 (Skin Fade +£4). They must be split apart by regex, and the split has to survive a service name that itself contains a hyphen.
  • dd.service-description is currently empty for all 20 services. Wire it anyway: the moment the owners type a description into Schedulista, it appears on the site with no code change.

C3 · The sync script

One file, one dependency (cheerio), no server. It runs in CI and writes a JSON file into the repo.

scripts/sync-services.mjs
import { load } from 'cheerio';
import { readFileSync, writeFileSync } from 'node:fs';

const SRC = 'https://perrins1.schedulista.com/';
const OUT = 'public/services.json';
const UA  = 'PerrinsBarbershopSite/1.0 (+https://perrinsbarbers.co.uk)';

const html = await fetch(SRC, { headers: { 'user-agent': UA } })
  .then(r => r.ok ? r.text() : Promise.reject(new Error(`Schedulista ${r.status}`)));

const $ = load(html);
const providers = [];
let current = null;

$('.services-list').children().each((_, el) => {
  const tag = el.tagName.toLowerCase();

  if (tag === 'h3') {                        // "Senior Barber - David"
    const [role, name] = clean($(el).text()).split(/\s+[-–]\s+/);
    current = { id: null, role: name ? role : '', name: name ?? role, services: [] };
    providers.push(current);
  }

  if (tag === 'dl' && current) {
    $(el).find('dt > a.widget-nav').each((__, a) => {
      const url   = new URL($(a).attr('href'));
      const label = clean($(a).text());       // "Men's Haircut - £24 (Skin Fade +£4)"
      const m     = label.match(/^(.*?)\s*[-–]\s*£\s*([\d.]+)\s*(?:\((.+)\))?$/);

      current.id ??= url.searchParams.get('provider_id');
      current.services.push({
        id:          url.searchParams.get('service_id'),
        name:        m ? m[1] : label,
        priceGBP:    m ? Number(m[2]) : null,
        priceLabel:  m ? `£${m[2]}` : '',
        note:        m?.[3] ?? null,           // "Skin Fade +£4"
        description: clean($(a).closest('dt').next('dd.service-description').text()),
        bookingUrl:  url.toString(),
      });
    });
  }
});

// --- guardrails: never publish a broken or empty list ---
const total = providers.reduce((n, p) => n + p.services.length, 0);
if (providers.length < 1 || total < 5 || providers.some(p => !p.services.length)) {
  throw new Error(`Parse looks wrong: ${providers.length} providers / ${total} services`);
}

const prev = JSON.parse(readFileSync(OUT, 'utf8'));
const next = { fetchedAt: new Date().toISOString(), source: SRC, providers };
logDiff(prev, next);   // ~10 lines: compare ids + prices, print to the Action summary
writeFileSync(OUT, JSON.stringify(next, null, 2) + '\n');

function clean(s) { return s.replace(/’/g, "'").replace(/\s+/g, ' ').trim(); }

Failure behaviour

A failed run does not write the file. The previous services.json stays live, the website keeps showing the last known-good prices, and GitHub emails the repo owner. A silent empty price list is the one outcome this design refuses to produce.

C6 · How the apps stay fresh

The website is rebuilt by the same commit that updates the JSON, so its HTML is always current. The mobile apps can't be rebuilt three times a day, so they fetch instead — with a bundled snapshot so the first paint is instant and the app works with no signal.

lib/services.ts
import bundled from '../assets/services.json';       // build-time snapshot
import AsyncStorage from '@react-native-async-storage/async-storage';

const REMOTE = 'https://perrinsbarbers.co.uk/services.json';

export async function getServices() {
  try {
    const res = await fetch(REMOTE, { cache: 'no-store' });
    if (!res.ok) throw new Error(String(res.status));
    const fresh = await res.json();
    await AsyncStorage.setItem('services', JSON.stringify(fresh));
    return fresh;
  } catch {
    const cached = await AsyncStorage.getItem('services');
    return cached ? JSON.parse(cached) : bundled;
  }
}

Render bundled immediately on mount, then swap in the fetched copy when it lands. No spinner, no empty state, no flash.

C7 · Local overrides

Schedulista owns name, price and availability. It has nowhere to store a category, a running order or a photo — so those live in a small file keyed by Schedulista's own service ID.

content/service-overrides.json (editable in the CMS)
{
  "1074623634": { "category": "Haircuts", "order": 1, "featured": true,
                  "blurb": "Consultation, cut, hot-towel finish." },
  "1074625171": { "category": "Beard",    "order": 6 },
  "1074670528": { "hidden": true }
}
  • A service in the feed with no override still appears — bottom of a "More services" group, default styling. New services are never invisible.
  • An override whose ID has vanished from the feed is logged in the CI summary and ignored. Never a crash, never a blank row.
  • hidden: true hides it from the list, but the deep link still resolves, so an old shared link never dead-ends.

C8 · Etiquette and the honest risk

  • This reads a public page belonging to the business itself, three times a day, with an identifying User-Agent. That is polite by any reading — but it is still an undocumented dependency.
  • Do this in Phase 0: email Schedulista support, say what you're doing, and ask whether they offer a services feed or API. If they do, swap the parser for it — same JSON output, everything downstream unchanged. If they say no, you have it in writing that they know.
  • If they ever block it, the overrides file becomes the source of truth and the owners edit prices in two places. Degraded, not broken.
C2

Booking inside our own interface

The first version of this plan sent the customer to Schedulista's own page. That is no longer the brief: the booking has to happen on our site, in our design. Everything below was verified against the live scheduler before a line of it was built.

Three findings that decide the architecture

ObservedConsequence
Access-Control-Allow-Origin is absent from every Schedulista responseA browser on our domain cannot call them at all. A server-side proxy is not optional.
_schedulista_session is SameSite=LaxEven a cross-site form POST would arrive without the session its CSRF token is bound to. Confirms the same conclusion by a second route.
No X-Frame-Options, no frame-ancestorsAn iframe would work — and is rejected anyway, because it would put Schedulista's light-themed pages inside a dark shop front. "Inside the website" was never the whole ask; "have that frontend" was.

The flow we drive, endpoint by endpoint

verified live — business code perrins1
GET  /schedule/perrins1/available_times_json
       ?service_id&provider_id&date=YYYYMMDD&time_zone=London
     -> [{ "start_time": "2026-08-25T09:00:00+0100", "provider_id": 1074010081 }, …]

GET  /schedule/perrins1/reserve_appointment
       ?service_id&provider_id&date=YYYYMMDD&time=<start_time>
     -> the details form, carrying an authenticity_token bound to the
        session cookies set on that same response

POST /schedule/perrins1/reserve_appointment?<same query>
       utf8, authenticity_token, fname, lname, email, country, phone,
       client_memo, send_sms, service_id, provider_id, date, time, commit
     -> 302  appointment created
        400  form re-rendered with field errors
        422  token and session disagree

Schedulista also exposes available_days_json, which would save a request per day. It answers 500 for every parameter combination its own page builds, so it is not used.

Our three routes

RouteDoesCache
GET /api/booking/availabilityFourteen days of free slots in one reply, fanned out in parallel upstream and grouped into morning / afternoon / evening.60s at the edge
GET /api/booking/holdFetches the details form and returns its session and CSRF token as an encrypted blob. Reserves nothing — Schedulista has no hold concept, and the UI says so.never
POST /api/booking/reserveValidates, unseals, submits. The only call in the product with a real-world side effect.never

The hold, and why it is sealed

A hold contains a live Schedulista session cookie. The browser has to hand it back on the final step, so it travels as an AES-256-GCM blob keyed on BOOKING_SECRET: encrypted so the client cannot read the cookie, authenticated so it cannot forge one, and stamped with a ten-minute expiry. The API stays stateless — no session store, no database — and no Schedulista credential ever reaches a browser in readable form.

Where "instant" actually comes from

Not from the animation. From never fetching anything at the moment someone is waiting for it.

MomentWhat has already happened
Pointer lands on a price row or the Book buttonAvailability for that barber and service is already being fetched.
Sheet opensA fortnight of slots is in memory, cached for 60 seconds and shared across every entry point.
A date is tappedNo network at all. The grid re-renders from the fortnight already held.
A time is tappedThe hold opens in the background while the customer starts typing their name.
Confirm is pressedOnly the reservation itself is left. If the hold aged out mid-typing, a fresh one is opened and retried once, silently.

The calendar

A month at a time, Monday first. Paging stops at three months — that is what the shop takes, it lives in booking.monthsAhead so the owners can move it, and assertWithinHorizon enforces the same number on the server. The arrows stopping is a courtesy; the server refusal is the rule.

  • One request per month. The API takes from/to and answers up to 42 days, so opening the calendar is one round trip and every day in that month is then free to browse.
  • The next month arrives before it is asked for, quietly, as soon as the current one lands.
  • Blank cells, not neighbours. Days outside the month are empty rather than greyed-out numbers from August and October — the single biggest source of clutter in a booking calendar, and nobody has ever tapped one on purpose.
  • Side by side or stacked, decided by onLayout on the panel rather than the window size, so the component responds to the space it actually has. Square cells via aspectRatio mean the grid never needs measuring and never reflows mid-animation.
  • Every date in the product is a YYYY-MM-DD string in Europe/London. A Date object carries the visitor's own timezone with it, and a phone set to Madrid must not move a Hertford appointment by a day.

Motion rules

  • Opacity and transform only. Nothing animates width, height or layout, so no frame ever waits on a reflow.
  • Enter-only step transitions, 170ms. Sequencing an exit into an entrance costs ~100ms of dead time on every tap and needs an animation callback to be reliable — one more thing that can leave the sheet stuck on the wrong step.
  • Changing day animates nothing at all. The month is already in memory, so the times list simply is different on the next frame. Animating a list that has no reason to move is where stutter comes from.
  • Reduced motion resolved once, at module load, and shared. Asking AccessibilityInfo inside every animated component meant each one rendered, settled, then started animating a tick later — which is the stutter it was meant to prevent.
  • Memoised leaves. A calendar day and a form field re-render only when their own props change, so paging a month does not re-render the form and typing a name does not re-render 42 days.
  • Native driver on device, inline transform on web. No spring, no bounce, no overshoot — traditional signage does not wobble.

Failure ladder

The rule: never report a booking we are not certain of.

What went wrongWhat the customer sees
A field is wrongThe error against the field. Validated on the server too — the client's check is manners, the server's is the trust boundary.
The hold expired while they typedNothing. A new hold is opened and the reservation retried once.
The slot went while they typedSchedulista's own message, and the time grid to pick again.
Schedulista is down or has changedA plain message and a button to their hosted page. Never a spinner that never ends.
The answer was unreadableIndeterminate — "we could not confirm that; ring the shop before booking again, so you do not end up with two appointments." Never a confirmation that might be a lie.

Keeping it safe

  • Whitelist. Only this shop's own barber/service id pairs pass the proxy, so the endpoint cannot be pointed at another Schedulista business.
  • Rate limit per IP: 60 availability lookups a minute, 8 reservations per ten minutes. ponytail: in-process counter, per server instance. Move it to the edge if booking spam ever becomes real.
  • Honeypot field. Filled in, the reply is a cheerful success and nothing is booked.
  • BOOKING_SECRET of 32+ characters, or booking refuses to start in production.

The canary

Three undocumented endpoints carry real bookings, so they get a tripwire of their own. npm run canary runs at 06:15 every morning and checks that slots still have their shape, the form still has its eight fields, and an invalid CSRF token is still rejected with 422. It never creates an appointment. When Schedulista changes something, a build fails instead of a customer's booking.

What has not been tested, and cannot be

Every step up to the reservation is verified against the live system. The final POST creates a real appointment in a real diary, so it has deliberately never been run — the closest safe probes are an invalid CSRF token (422, as expected) and a valid token with invalid data (400, with the field errors the UI renders). Before launch the shop should make one booking through the site and cancel it from the confirmation email.

Also: this is a heavier use of Schedulista than reading a public page. Email their support, say what the site does, and ask whether they will support it or offer a proper API. If they do, only server/schedulista.ts changes.

Why a CMS and not a JSON file in GitHub

A JSON file is free and needs no account — and one missing comma from a busy barber breaks the build on a Saturday morning. Sanity's free tier gives a hosted editor that works on a phone, handles image uploads and cropping, and serves the same JSON to the website and both apps from one API. Cost at this scale: nothing.

If they'd rather own everything in git, Decap CMS gives a similar admin screen backed by the repo. Same shape, slightly rougher editing.

E

Design system

Traditional barbershop, read as: dark panelled walls, gilt signwriting, brass, no gloss. The restraint is the point — one accent, hairline rules, near-square corners, almost no motion. Nothing rounded and glowing.

Palette

ink#0B0B0D
panel#131316
panel-2#1A1A1E
gold#C6A24A
gold-lift#E6CE86
gold-deep#8C6F2A

  • Gold is the only accent. It marks exactly one thing per screen: the primary action. Everything else is cream, muted, or a hairline.
  • Hairlines are rgba(198,162,74,0.20) — gold at low alpha, never grey. That single choice is what makes the dark read as panelled rather than as a generic dark mode.
  • Status colours are separate and never used decoratively: #6FBF73 open, #C4574F closed.
  • The neutrals carry a slight warm bias (cream, not white; #0B0B0D, not #000) so gold sits on them without vibrating.

Typography

RoleFaceUsed for
DisplayYeseva OneShop name, screen titles, barber names, prices — the only face allowed to carry gold. Closest match on Google Fonts to the logo's Victorian high-contrast serif. One token, font.display; see the note below before treating it as confirmed.
Body and UIArchivo 400/500/600Everything else. Grotesque, slightly industrial, excellent tabular figures for the time grid.
LabelsArchivo 600, 11px, letter-spacing: .18em, uppercase"SERVICES", "EST 1999", section eyebrows.
  • Type scale, and stay on it: 11 / 13 / 15 / 17 / 20 / 26 / 34 / 48.
  • Dot leaders on the price list, the way a barbershop board is set. They are not decoration: they do the job tabular figures would, letting the eye track the row instead of the digits, so the display face can keep its own letter widths.
  • Body copy capped near 65 characters. Every screen is set left — a centred column of evenly spaced blocks is what a page looks like when nobody decided anything.

The typeface is a best match, not an identification. A 200px raster is not enough to be certain which face the logo uses. Yeseva One ships as the closest thing on Google Fonts; Rye is the alternative if the shop wants the more western reading. Ask whoever drew the logo, or run the original artwork through a font-identification service, and change font.display — nothing else in the codebase names a typeface.

Form and motion

  • Radius 2px on cards and buttons, 999px on status pills only. Traditional signage is square-cornered; rounded-2xl would make it read as a startup.
  • No drop shadows. On a dark ground they turn to mud. Separate surfaces with a 1px gold hairline plus a rgba(255,255,255,.04) top edge.
  • Texture: a 3% film-grain overlay across the app background. Enough to stop flat black looking like a default. Nothing more.
  • Motion: 180–220ms ease-out fades and a 6px rise on list entry. No springs, no bounce, no parallax. Full prefers-reduced-motion support.
  • The barber pole appears once, as a 3px diagonal-striped rule under the header. Using it twice makes it a theme park.

Screens

Five routes, identical on web and native. Web renders them as sections of one scrolling page plus real URLs; native renders them as tabs.

1 · Home — the front door

The brief says: open with information about the business and a Book Now button. Order, top to bottom:

  1. Logo mark on ink, centred, with EST 1999 letterspaced beneath.
  2. One line of positioning from the CMS — "Hertford's barbershop, on Old Cross since 1999."
  3. Book Now — solid gold, full-width on mobile, the only gold-filled element on the screen.
  4. Status chip — "Open now · closes 17:30" or "Closed · opens Tue 09:00", computed live in Europe/London.

App Store guideline 4.2 — plan for this or lose two weeks

Apple rejects apps that are a website in a wrapper. An app whose only function is "open Schedulista" will be rejected. The native capabilities below are not decoration; they are what makes it approvable, and each is genuinely useful:

  • Full price list readable offline, from the bundled snapshot.
  • Live "Open now / Closed" computed on device against Europe/London.
  • One-tap call and one-tap directions into the native maps app.
  • "Your usual barber" — remembers David or Ben locally and defaults the Services tab to them.
  • Native share sheet for a service and its price.
  • Gallery with a native full-screen viewer and pinch-zoom.

Submit under Perrin's own developer accounts, and use real shop photography in the store listing.

As built

Everything above is the plan. This section is what the repository actually does, where it went further than the plan, and where the plan was wrong.

Nothing in the code knows a barber's name

The plan had content.json holding a category and an order for every service, keyed by Schedulista's ids. That worked, and it had one fatal property: a barber added in Schedulista arrives with ids nobody has ever seen, so every one of their services fell into "More" and the new chair looked broken until somebody edited a JSON file. The shop would have had to ring a developer to hire a barber.

So the grouping is derived from the only thing we know about a service we have never met — its name. classify() in lib/services.ts sorts a name into Haircuts, Beard, Haircut & Beard, Colour or Extras; the owners' overrides still win where they exist, and the override block now ships empty. Against the live list this reproduces the hand-written grouping exactly.

Everything else that used to assume two barbers now counts:

  • One signature service per barber is taken onto the front page in rotation, so no barber can be silently left off it.
  • The price list gives each barber a tab. Two share the width; three or more and the row scrolls sideways rather than squeezing names into unreadable columns.
  • With one barber the "who would you like?" step disappears from the booking flow and the price list loses its tabs, because there is nothing to choose.
  • "In the chairs: …", the Book now subtitle, the "all N prices" link and the sheet's footnote are all generated from the live list.
  • The chosen barber on the price list is remembered by id, not by index. A barber leaving must not silently switch a regular onto somebody else's prices because the array got shorter.

Live, not nightly

The plan had the sync running three times a day into services.json. That is still there — it is what gives the first paint real prices with no round trip — but it is no longer the freshest thing a customer sees. server/catalog.ts re-reads the scheduler page at request time behind a ten-minute cache and serves it from GET /api/services. A barber added at nine is bookable before ten, with no deploy.

Both paths run the same parser. Two parsers would eventually disagree about what a service is called; the cheerio dependency is gone and the shared parser is plain regex, because it has to bundle for the server runtime as well as for Node.

The server's booking whitelist consults the live list too, with the build-time list as the floor: a new pair is accepted without a redeploy, and a scheduler outage cannot lock customers out of services that have not changed.

Three months, enforced twice

The calendar pages three months and the arrows stop. That is a courtesy. assertWithinHorizon refuses the same range on the server, because a hand-typed address should not be able to hold a slot next Christmas.

The brand arrived after the build

Sections E and F were written from a 200px raster and a guess. The shop then supplied the real artwork — the circular badge, and a photograph of the front — and everything downstream of that guess had to be redone.

  • The palette is black and gold, and the gold is not chosen but sampled: #C6A43C is the exact value of the lettering on the badge, read off the file, and the two status colours are the rose and its leaves read the same way. The black is a true neutral: the first version carried a little warmth and read as brown next to the gold. Measured on the page ground: cream 17.0:1, goldLift 11.5:1, muted 9.4:1, gold 8.5:1, mutedDim 5.6:1, and gold on a panel 7.9:1. Because gold clears AA at label size, the small capital labels are plain gold; goldLift is reserved for hover and for prices. The budget is written into the header of theme.ts.
  • The button label is the page's own black on gold, not the reverse. The obvious way round measured 3.2:1 and would have shipped a failing CTA.
  • The display face is LHF Old Tom, the shop's own, licensed and supplied by the shop, so the type on the page and the lettering on the badge are the same drawing rather than a near miss. Two of its five cuts are loaded: Plain for headings, prices, names, addresses and every small capital label, and Poster Letter, capitals only, for the shop's name. The layered Poster Full and Poster Highlights pair is in the repository and unused, because the badge does not use the inline effect. Outfit is the text face, a rounded geometric matched to the shop's printed card. Yeseva One, Archivo and the Bodoni Moda stand-in are all gone.
  • One measurement drove a global correction. Old Tom's capitals are exactly as tall as Outfit's, 71 against 70 at the same point size, but an H is 46.8 units wide against 70.6: it is a third narrower, so at a matched size it covers much less of the line and reads as small type. Every display size goes through dsize(), which scales by 1.3. It is an optical correction, not a change to the scale, and body copy is untouched.
  • The wordmark sizes itself. The glyphs of "PERRIN'S" in Old Tom Poster Letter measure 3.282 ems and the tracking is a fixed number of points on top of that, so Wordmark solves for the size that fits the room it is handed. Folding the tracking into the ems was right at 78pt and 1.4px short at 44pt, which once put an ellipsis in the shop's name on a phone. The front page sizes the badge first and gives the mark the rest, which is why there is no type breakpoint anywhere between a 320px phone and a 1600px desktop.
  • The badge is the artwork as supplied, transparent, on no plate of ours. The crop is done in the layout instead of to the file: the drawn part covers 416 of the artwork's 640 points, so the image is drawn at size / 0.65 and centred, and the size prop means the size the badge appears. Just over half the badge is pure black and therefore invisible against the page; the reverse of it, cream linework instead of black, was built and the shop preferred the original.
  • The front page is a composition, not a stack. Badge and name locked up across the top, the hashtag under them, a rule, then the introduction against the one gold button, then the hours and the address. The photograph is not on it at all: it lives on Visit, where it is doing a job, and under the badge it only competed with it. On one column the button moves above the introduction, because seven lines of it is most of a phone screen and the thing the page exists for cannot be below that.
  • The barber pole is gone. It was drawn, then built properly, then removed on the shop's instruction. Its last surviving trace was the favicon, which is now the crossed scissors from behind the badge lettering: two strokes and two rings, legible at 16px where the full badge is a smudge.
  • No long dashes anywhere a customer can read. Sixty of them came out of the content and the screens, and npm run check:dashes fails the build if one gets back in.

Owner control, extended

Section D promised a CMS for the words. The words were the easy half. content.json now also holds:

BlockWhat the owners get
design.paletteEvery colour in the product. Nothing else in the codebase holds a hex value, and the hairline rules are derived from the accent, so changing gold changes them too.
design.corner, design.densityCorner radius from square-signage to modern; a multiplier on every gap and margin.
layout.homeThe order of the blocks down the front page, as a list of names. Move a line to move a block; delete one to remove it.
bookingHow far ahead people may book, how many empty months the calendar will skip, whether text reminders are offered.
content/legal.jsonThe privacy policy and the terms, as headings and paragraphs.

Every one of them is read defensively: a bad number is clamped, a misspelled block name is skipped, a missing section falls back to what ships. The people editing this file are barbers, and a saved typo must never take the site down. OWNERS.md explains all of it in plain English.

Legal

/privacy and /terms, reachable from the web footer, from Visit inside the app, and from a link under the Confirm button. They were written to describe what this code actually does — not copied from another shop: the details go to Schedulista and nowhere else, nothing is written to a database of ours, the only thing stored is on the customer's own device, there are no cookies or analytics or trackers of any kind, and the app asks the phone for network state and nothing else. {phone}, {email}, {address} and {monthsAhead} are substituted from the settings the rest of the app uses, so a policy cannot quote a number that changed elsewhere.

Store readiness

The plan listed the logo as blocking submission, and it was: neither store accepts a build without a 1024px icon. That is resolved — the app icon, the adaptive icon, the splash and the Play icon are all the real badge, at the inset each store needs, and the iOS one is written without an alpha channel because Apple rejects an icon that carries one. scripts/make-icons.mjs survives to draw the favicon and nothing else. app.json carries the iOS privacy manifest, the Android permission block (network state only; camera, location, storage and microphone explicitly blocked), the adaptive icon and the splash configuration. STORE.md lists what is in the build and what only a person with the shop's accounts can do.

What is still not true

  • The final reservation POST has never been run for real. Every step up to it is verified against the live system, but creating an appointment in a working shop's diary to prove a point is not a thing to do without being asked. One test booking, then cancel it.
  • The font licence needs checking. LHF Old Tom is in the build. Confirm with Letterhead that the licence covers a website and two app bundles, not only a desktop machine.
  • The gallery does not exist, on purpose. There are no photographs.
